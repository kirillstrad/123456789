# Lighting patch 4b: one playable combat brazier

The normal combat environment now initializes one off brazier.a at (6.8, 10.8). A per-door-scene WeakMap shares its light registry between the environment and the existing combat interaction owner. The existing application imports these factories already, so no duplicate keyboard handler, simulation timer or main.js replacement is introduced. Legacy controller-only fixtures remain door-only unless their environment enables the light context.

The environment publishes both door and light targets and contributes the brazier geometry and lit emitters to the existing ASCII render and lighting loops. Authored solid footprints are conservatively represented as scene-local circles in the shared combat map; navigation and door sweep checks see them. The original global obstacle template is untouched. This conservative collision conversion needs visual clearance review and is not an arbitrary-yaw light-placement guarantee.

The existing frame selector and F intent feed one owner. Ignite intent checks the full seven-unit budget before navigation and again during approach. The shared planner uses live combat obstacles. Arrival turns toward the source, then hands off to the existing guarded ignition controller. Its contact marker pays exactly six LAMP and publishes lit geometry. Each owner step advances the world once. Door behavior is retained, including both-side approach candidates and contact animation.

Manual movement cancels approach; combat commands cancel approach but do not interrupt an active ignition animation. Pause, freeze, blur, gallery transitions and reset use the application's existing cancellation hooks. Reset clears ignition and light state before door/world reset. Snapshot diagnostics include light states and emitter count. No gallery ignition or other eight model placements are claimed. Source-specific hand fitting remains for the next iteration.

New tests exercise the real F intent handler, ordinary navigation, exact payment, single simulation ticking, insufficient budget, blocked planning, manual cancellation, inactive ownership, reset and a door regression with the light present. A Chromium check starts the normal app, uses pointer selection and F, verifies payment and emitted light, captures a screenshot and verifies restart. The enemy is moved away only in the browser fixture to isolate the interaction. CI and human visual acceptance have not yet been established for this patch. No camera or hero palette changes are included.
